# Design and rationale

Author: Lofrano Tecnologia. Development version 0.1.0.

## Separate protocol acceptance from interpretation

The sink is a deliberately small state machine over a bounded nonblocking CRLF reader. It treats MIME as opaque data except top-level wire/header restrictions. SMTP final acceptance means complete local publication, not successful interpretation of every MIME part. This separation lets tests distinguish a transport/integration failure from a malformed attachment.

Only a numeric loopback socket is created. Envelope validation is string processing; no recipient hostname reaches a resolver, SMTP client or socket constructor. The sole sending application is the independent synthetic fixture client, also using numeric loopback. It disables opportunistic STARTTLS and supplies ASCII quoted-printable wire bytes for UTF-8 text.

## Storage ownership and reservations

A lifetime flock rejects competing sinks. A separate flock shared by readers, combined with a mutex for server threads, protects all admission accounting and publication. Accounting includes stage metadata, markers and every raw append before write. Four transactions cannot each reason from the same stale free-space count. Message slots are reserved as well as bytes.

Directories, not individual files, are renamed. Therefore a concurrent reader sees either no delivery or both envelope and raw bytes. There is no independently visible half-message. IDs come from validated committed state at rename time, not from stage creation or a timestamp. Equal bytes have no special identity. Files are synced before rename and the parent directory afterward, but only process-crash scenarios are the documented recovery target.

A private mailbox is a capability granted by its caller. The code rejects foreign layout, bad ownership/modes, hardlinks and leaf symlinks. It is not a sandbox against hostile code under the same UID, untrusted ancestors, filesystem replacement races by that UID or a compromised OS. Cleanup only unlinks the known files in recognized stages, never arbitrary recursive paths. Entry enumeration, orphan count and file sizes are bounded before deletion. Crashes before a stage marker exists fail closed on restart.

## MIME and resource containment

The mail gem provides MIME parsing and decoding; the application does not reimplement its grammar. The public inspector launches one owned constrained Ruby process and supplies bounded stdin. The parent concurrently pumps input, stdout and stderr with an absolute monotonic deadline, kills the process group on failure and waits. Linux address-space, CPU, descriptor and core limits complement the wall deadline.

The direct-part walk is iterative. It checks depth before descent and total queued/visited parts before scheduling children. It does not call recursive `attachments` or `all_parts` helpers. Crucially, accessing mail objects can already expand their bodies. The `Mail::Body#split!` probe records the real expansion method in pinned mail 2.9.1; adversarial tests assert that parser expansion did occur before traversal rejection. We do not describe this walk as preparse depth protection. A worker may fail by resource termination instead of returning a semantic limit code.

Decoded byte accounting includes every leaf, text and attachment, before text normalization. Bad later parts invalidate the whole result; prior decoded data is not returned as a partial success. Base64 is canonical-validated before mail decoding. Quoted-printable equals syntax is checked before mail decoding. Unsupported charsets and nested message types have explicit errors rather than lossy fallback. Filenames and metadata remain untrusted values, never path components.

## Regression strategy

Tests use independent fixed wire bytes and expected byte arrays, not a message generated by the same parser. Coverage includes Portuguese UTF-8 text, dot transparency, two independently encoded attachments, mixed accepted/rejected recipients, RSET reuse, null senders, rejected syntax, duplicate deliveries, concurrent byte/slot reservations, ownership conflict and foreign stages. Fault gates pause immediately before publication and immediately after publication/before 250, allowing process termination and restart tests on both sides of the uncertainty boundary.

Resource tests cover raw overflow, overlong lines, missing terminator, slow trickles, a fifth session, four SMTP sessions against near-full storage, wide/deep MIME, malformed encodings and owned worker timeout/output limits. They are regression checks, not benchmarks or evidence of broad standards/security compliance.

## Trade-offs

Fixed conservative limits and a small supported subset make the observable contract stable, at the cost of rejecting legitimate mail outside it. Logical quotas are not disk-block quotas. The application cannot interrupt a stuck local filesystem syscall. There is no queue, delete API, authentication, TLS or external delivery. A process crash after publication can lose the success reply, so exactly-once delivery is impossible here without an application-level protocol outside this project.

The process supervisor keeps its direct child unreaped until captured output pipes reach EOF, so an unreaped leader anchors its process-group ID while output is pending. Failure cleanup signals that group before waiting. After any successful wait or observed loss of wait ownership it sends no signal to the numeric PID/PGID. The supplied helpers are fixed programs; this is not a daemon discovery or arbitrary detached-descendant cleanup API. One supervisor must own each child wait. Real normal, hanging and flooding child regressions record wait/signal order and reject every attempted signal after reap.
